# 同行评审清单（Peer Review Checklist）

> 适用：所有 `feature/*`、`docs/*`、`test/*` → `develop` / `main` 的 PR
> 依据：`docs/team-agreement.md`（24 小时响应）、`docs/team/dor-dod.md`（DoD）、PR 模板
> 关联：Lab 7「质量门禁与 SonarQube」四件套之一

## 一、什么时候用

1. 作者提 PR 前，先按「作者自检」过一遍；
2. 评审人点 `Approve` 前，必须逐项过「评审人清单」；
3. 任一 `blocking:` 未解决，不得 Approve；
4. 合并后由作者/评审人把结果登记到文末「评审记录」。

## 二、作者自检（提 PR 前）

- [ ] 关联了 PBI / Issue，标题写清范围（一个 PR 只做一件事）
- [ ] 本地 `mvn -B -f backend/pom.xml test` 或对应模块测试通过
- [ ] 改了 domain/application 时，`mvn verify -DskipITs -Djacoco.skip=false` 通过（覆盖率 ≥70%）
- [ ] 改了接口/事件/表结构时，补了对应测试与文档（ADR / README / http 示例）
- [ ] 没有提交 `target/`、`node_modules/`、`.env`、密钥、个人 IDE 配置
- [ ] PR 描述写了「改了什么 / 怎么验证 / 影响范围 / 回滚方式」
- [ ] CI 至少后端/前端两项已绿（未绿先查再请求评审）

## 三、评审人清单

### 3.1 需求与范围

- [ ] PR 与关联 PBI/Issue 一致，没有夹带无关改动
- [ ] 验收标准能在 PR 描述或测试里找到对应证据
- [ ] 没有把「以后再做」的 TODO 混进本次范围（除非明确标注）

### 3.2 设计与架构

- [ ] 分层正确：domain 不依赖 Spring/JPA；repository 接口在 domain、实现在 infrastructure
- [ ] 聚合只引用其他聚合的 ID，不跨聚合持有对象/事务
- [ ] 跨上下文只走 `api` 或事件；没有直接依赖别人的 infrastructure
- [ ] 新事件/端口有幂等与失败处理（outbox、processed_event、重试/死信）
- [ ] 没有为了通过测试而放宽 ArchUnit 规则

### 3.3 正确性与边界

- [ ] 入参校验完整（空值、长度、范围、枚举），错误码符合 [`docs/错误码.md`](../错误码.md)
- [ ] 权限校验在应用层/接口层都有：作者/管理员/课程成员按公开策略校验；公开问题允许匿名读，课程内写操作必须成员/作者
- [ ] 幂等：重复提交、重复消费、重复标记已读不会产生第二条数据
- [ ] 事务边界正确：写库 + 发事件在同一事务/outbox，不在 Controller 里开事务
- [ ] 并发/计数使用原子 SQL 或乐观锁，避免读改写丢更新
- [ ] 软删除后搜索、推荐、列表、详情行为一致

### 3.4 测试

- [ ] 新增/修改行为有对应测试，测试名能说明业务规则
- [ ] 测试断言的是行为，不是实现细节；没有 `Thread.sleep` 等脆弱等待
- [ ] 领域测试覆盖正常 + 异常 + 边界；应用测试覆盖权限与幂等
- [ ] 集成测试（Testcontainers）在涉及 Flyway/搜索/通知/声誉时更新
- [ ] 没有删除/跳过别人的测试来让 CI 变绿

### 3.5 安全

- [ ] 新接口有认证与角色校验；管理接口仅 ADMIN
- [ ] 状态变更接口有 CSRF 防护；会话/Session 逻辑没有绕过
- [ ] 输入不拼 SQL；日志不打印密码、token、完整 Cookie、个人敏感信息
- [ ] 文件/图片/链接类输入有类型与大小限制
- [ ] 依赖没有引入已知高危漏洞（必要时 `mvn dependency:tree` 核对）

### 3.6 数据与迁移

- [ ] Flyway 脚本命名递增、可重复执行安全；没有修改已发布的旧脚本
- [ ] 新表/索引考虑查询与唯一约束；字符集 `utf8mb4`、时间字段统一
- [ ] 迁移向后兼容（先加列/表，再改代码；删除分两步）
- [ ] 回滚/修复方案在 PR 描述里写清楚

### 3.7 可观测性与运维

- [ ] 关键路径有日志（带 eventId/aggregateId，不含 PII）
- [ ] 新增定时任务/消费者有指标或至少日志可查
- [ ] 配置项有默认值，能通过环境变量覆盖；没有硬编码本机路径
- [ ] README / `http/*.http` / compose 示例随行为更新

### 3.8 文档与提交

- [ ] 公共行为变化更新了 README / ADR / docs/final 对应页
- [ ] Commit message 符合 `feat|fix|docs|test|chore(scope): ...`
- [ ] 没有大段注释掉的代码、调试输出、临时脚本
- [ ] PR 文件数/行数合理；超大 PR 已说明为什么不能拆

### 3.9 CI 与门禁

- [ ] `后端构建与验证`、`前端构建` 绿；PR→main 还需 `容器镜像构建` 绿
- [ ] 覆盖率门禁通过（四个 domain ≥70%）
- [ ] 集成测试（Testcontainers）通过，没有 `continue-on-error`
- [ ] 若改了 CI/分支保护，已同步 ADR-009 与规则集说明

## 四、评论约定

| 前缀 | 含义 | 是否阻塞 |
| --- | --- | --- |
| `blocking:` | 必须修改，否则不能合并 | 是 |
| `question:` | 需要作者解释/确认 | 视回答 |
| `nit:` | 风格/命名建议，可不改 | 否 |
| `praise:` | 值得保留的做法 | 否 |

- 评论对事不对人，指出问题时给出文件/行号与建议；
- 作者对 `blocking:` 逐条回复「已改/不改+理由」，不改的由评审人确认；
- 24 小时内给出首次评审；超时在群里升级。

## 五、Approve 条件

同时满足才可 Approve：

1. 无未解决的 `blocking:`；
2. CI 必需检查全绿；
3. 覆盖率不低于门槛；
4. 至少一位非作者的评审人（main 需 2 位，含 SM/PO）；
5. PR 描述与变更一致，回滚方案可执行。
