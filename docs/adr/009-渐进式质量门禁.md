# ADR-009: CI 质量门禁（渐进启用 → 全量硬门禁）

## 状态

已完成。

- 2026-11-16（S3 收口）：全仓 27 模块 `mvn verify -DskipITs` 通过，五个后端阶段 + 前端阶段全绿；
- 2026-11-17：移除集成测试 `continue-on-error`，`CampusOverflowFlowIT` 改为硬门禁；
- 2026-11-18（S4 收口）：删除 `SPRINT_MODULES`，单元测试与覆盖率门禁恢复全量 `mvn test` / `mvn verify`。

## 背景

项目初期只实现了 Identity 与 Q&A，若 CI 一上来跑全仓测试，未实现模块的红叉会淹没真实问题。因此采用“渐进式质量门禁”：按 Sprint 把已实现模块加入 `SPRINT_MODULES`，范围随 Sprint 扩容；集成测试早期允许失败，仅作提醒。

到 S3/S4，四个上下文与前端均已实现，渐进式白名单反而会漏掉白名单外模块（identity application/infrastructure、qa infrastructure、shared-kernel、bootstrap 等）的测试；V3 §8.3 也要求 S3/S4 的集成测试必须通过。门禁需要从“渐进”切换为“全量硬门禁”。

## 决策

1. **文档改动不单独设 `paths-ignore`**（2026-11-17 修正）：只改文档的 PR 不会产生必需的「后端构建与验证 / 前端构建」检查记录，检查长期 pending 会阻塞合并；仓库已转 public，Actions 分钟数不受限，不需要为该场景做特殊处理。
2. **单元测试全量通过**（2026-11-18）：阶段 2 执行 `mvn -B -f backend/pom.xml test`，覆盖全部 27 个模块；删除 `SPRINT_MODULES` 变量，不再维护模块白名单。
3. **覆盖率门禁全量**（2026-11-18）：阶段 4 执行 `mvn -B -f backend/pom.xml verify -DskipITs -Djacoco.skip=false`，四个 domain 模块行覆盖率均须 ≥ `domain.coverage.minimum=0.70`。
4. **集成测试硬门禁**（2026-11-17 起）：阶段 5 执行 `mvn -B -f backend/pom.xml verify -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false`，由 failsafe 运行 `CampusOverflowFlowIT`（Testcontainers 起 MySQL 8.0.39 + Redis 7），失败即阻断合并；显式设置 `DOCKER_HOST=unix:///var/run/docker.sock`、`DOCKER_API_VERSION=1.43`、`TESTCONTAINERS_RYUK_DISABLED=true`。
5. **Actions 用量控制**（V3 §8.5）：启用 Maven 依赖缓存与 `concurrency`（同一 ref 新提交取消旧运行）；容器镜像构建只在 `main` push 与 `PR→main` 时执行。

## 后果

- `develop` 的必需检查为「后端构建与验证」「前端构建」，`main` 另需「容器镜像构建」；由于 `enforce_admins=true`，管理员也不能绕过。
- 全量测试比 Sprint 范围慢（多出 identity/qa 的 application/infrastructure、shared-kernel、bootstrap），但换来白名单外模块的真实覆盖；CI 缓存 + concurrency 抵消大部分耗时。
- 集成测试依赖 GitHub Runner 的 Docker daemon 与 Docker Hub 拉取 `mysql:8.0.39`、`redis:7-alpine`；若 Docker Hub 限流，需改用镜像缓存或重试。
