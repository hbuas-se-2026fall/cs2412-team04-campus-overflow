# ADR-009: CI 流水线集成测试容错策略

## 状态：已完成（S3 收口 2026-11-16：全仓 27 模块 `mvn verify` 通过；2026-11-17 收紧：移除集成测试容错，改为必须绿）

## 背景

渐进式质量门禁的目的是"让每个 Sprint 的 CI 有意义"：初期只把已实现的模块放进门槛，避免未实现模块的红叉把真实问题淹没。随着 Sprint 推进，门禁范围与严格度都应收紧，最终与 V3 §8.3 的"各 Sprint 质量门槛"对齐。

## 决策

1. **文档改动不单独设 `paths-ignore`**（2026-11-17 修正）：早期曾计划用 `paths-ignore` 跳过 `docs/**`，实际未启用——因为只改文档的 PR 不会产生必需的「后端构建与验证 / 前端构建」检查记录，检查会长期 pending 反而阻塞合并；且仓库已转为 public，Actions 分钟数不再受限，无需为该场景做特殊处理。
2. **单元测试（`mvn test`）必须通过**：阶段 2 按 `SPRINT_MODULES` 跑当前 Sprint 范围，范围随 Sprint 扩容（S0 shared-kernel + identity → S1 加 qa → S2 加 reputation → S3 加 discovery）。
3. **集成测试（`mvn verify`）必须通过**（2026-11-17 收紧，对应 V3 §8.3 S3/S4 门槛）：阶段 5 移除了 `continue-on-error: true`，`CampusOverflowFlowIT`（Testcontainers 起 MySQL/Redis）失败会阻断合并。阶段 5 用 `-Dtest=none -Dsurefire.failIfNoSpecifiedTests=false` 让 surefire 不重复执行单测，只由 failsafe 执行 `*IT`。
4. **Actions 用量控制**（V3 §8.5）：启用 Maven 依赖缓存；启用 `concurrency`（同一 ref 的新提交自动取消旧运行）；容器镜像构建只在 `main` push 与 `PR→main` 时执行。

## 验收与证据

- 阶段 1~5 的名称即分支保护的必需检查上下文：`后端构建与验证`、`前端构建`；`main` 另需 `容器镜像构建`。
- 全仓 `mvn verify` 通过记录：`docs/reports/release-v1.0.0-verification.md`、`docs/final/03-quality.md`。
